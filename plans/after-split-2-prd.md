## Problem

From the user's side: a slice or planner working in a worktree runs `risa doc <role>` and `risa project-check`, and both read the main checkout's `risa.json`, docs and golden prompts, not the worktree's. A slice that changes a role doc, its additions or the config sees main's version and checks main's files; its own change is invisible until it lands. The cause: every session is opened from a shell that `find_repo` set up in the main checkout, so it carries `RISA_CONFIG` naming the main checkout's file, and `find_repo` keeps any `RISA_CONFIG` it finds, so it never looks at the worktree.

## Solution

Every risa command run in a worktree of a listed repo reads that worktree's `risa.json` (falling back to the main checkout's when it has none), unless the user pinned another config. Risa tells its own inherited choice from a pin by a mark it sets beside it. Stack hooks still run from the main checkout, and the backlog, registry and session state stay the main checkout's. Removing a worktree from inside it still finishes its registry steps.

## User stories

1. As a slice agent, I want `risa doc` and `risa project-check` in my worktree to read my worktree's config and files, so that I check my own change (RISA-972).
2. As a planner, I want the role docs and preferences my brief reads (`risa doc planner`, the skeptic brief) to be my branch's, so that a docs change on my branch shows in my own session (RISA-972).
3. As a user or a project's test, I want a `RISA_CONFIG` I set myself to win in any checkout, so that a pinned config (Caretook's project-data test, a sample project) is never replaced (RISA-972).
4. As any agent in a worktree, I want `risa backlog` to keep writing the main checkout's backlog under the main checkout's paths and ids, so that a branch's config never skews the live backlog (RISA-972).
5. As a slice with a stack, I want the stack hooks to run from the main checkout as today, so that a worktree made from an older branch still brings its stack up and down (RISA-972, B-846).
6. As an orchestrator or planner, I want `risa rm` from inside my own worktree to finish its registry and backlog steps, so that removing the worktree whose config I read doesn't fail halfway (RISA-972).

## Implementation decisions

- **Which config a command reads** (the machine config's `repo` answer, `machine.mjs`): given the current directory, it prints the main checkout and the config path: the top of the current checkout's `risa.json` when that file exists, else the main checkout's. One pure function decides it from the checkout's top, the main checkout and whether the file exists, so it tests alone; the command's output keeps its two lines, so both bash callers read it unchanged.
- **Inherited or pinned** (`find_repo` in `lib.sh`): when the machine config lists the repo, the command takes the found config if `RISA_CONFIG` is unset or equal to `RISA_CONFIG_FOUND`, and exports both to the found path; otherwise it leaves `RISA_CONFIG` alone. With no machine config nothing changes: the config loader already reads the tool's own checkout, or the current checkout under an installed package.
- **The backlog command** (`bin/risa`'s backlog branch): with the machine config listing the repo, it takes the main checkout's `risa.json` when `RISA_CONFIG` is unset or equal to the mark, else keeps the pin; it never reads a worktree's.
- **Stack hooks' directory** (`stack_hook`, `runHook`'s top): the main checkout of the repo the config file is in (the first entry of `git worktree list`), else the config's folder when it is in no checkout, as today.
- **`rm`** (`rm.sh`): before `git worktree remove`, a `RISA_CONFIG` under the worktree being removed is re-pointed, with its mark, at the main checkout's `risa.json`; the steps after it (registry done, hot cleared, run log) read that.
- **The tests' environment** (`test-env.mjs`): `RISA_CONFIG_FOUND` joins the session variables it clears.

## Testing decisions

- The config choice: unit tests of the pure function (a worktree with its own `risa.json`, one without, the main checkout itself), and of `machine.mjs repo` through a temp repo with a worktree (prior art: `machine.test.mjs`'s "the bash side").
- Inherited vs pinned: bash tests that source `lib.sh` in a temp worktree with a machine config listing the repo: an inherited `RISA_CONFIG` with its mark becomes the worktree's; a `RISA_CONFIG` with no mark, or a different one, stays; `bin/risa backlog` from the worktree reads the main checkout's config with the inherited pair and keeps a pin. One end-to-end case: `risa doc planner` in the worktree prints the worktree's planner additions.
- Stack hooks: `hooks.test.mjs`'s B-846 case gains a config inside a worktree: the hook runs at the main checkout's top, from Node and from `stack_hook`; a non-stack `run_hook` still runs at the worktree's top.
- `rm`: a `stack.test.mjs` case removes a worktree with `RISA_CONFIG` (and its mark) naming that worktree's config, and the registry step still runs.
- The tests' environment: `test-env.test.mjs` adds the mark to the variables that never come through.

## Out of scope

- Caretook's side: dropping its `RISA_CONFIG` pin in project-data.test, once it takes a release with this.
- Which config Node scripts started directly (not through `risa`) read: they read the inherited `RISA_CONFIG`, as today.
- RISA-994 (tests failing in the main checkout with the session variables unset): fixes-tooling.
- Reading hook commands from the main checkout's config while the rest comes from the worktree's.
