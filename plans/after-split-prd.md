## Problem

Risa moved out of Caretook into its own repo (RISA-543). What it left behind shows on every machine that runs it:

- The tests fail when run from any shell a risa session set up: 217 on one machine read Risa's own `risa.json` instead of the fixture project's, and 10 on the other read the live sessions, usage readings and dispatcher of the machine itself. A slice or orchestrator running `pnpm check` inside its session can't tell its breakage from the environment's.
- On an old git (2.24) a fixture's failed `git init -b` let the suite run its git commands in the real checkout and empty its index.
- A project that installs Risa from a tag can't import the verdict reader, the verdict fixtures or the docs budget by package name, and importing the budget runs it.
- A worktree sees its main checkout's config, docs and golden, so `risa doc` and `risa project-check` in a slice check main's files, not the slice's (RISA-972: the follow-on topic `after-split-2`).
- In a repo without a stack, `risa status` says the testDb hook failed; the generic docs print `prd doc …` where a project's command name belongs; and on a new machine the inbox never opens, with nothing to say why unless someone runs `dispatch --dry-run`.

## Solution

A test run is hermetic whatever shell starts it: the fixture project's config, no session's state, and a clear stop on a git too old to build its fixtures. Install refuses that git too. A project imports the CI and docs-budget parts it needs by package name. `risa status`, the generic docs and the dispatcher say what is true in a stackless repo, in the project's own command name, and on a new machine.

## User stories

1. As a slice or orchestrator agent, I want `pnpm check` inside my session to pass on a clean tree, so that a failure I see is my change's (RISA-975, RISA-979, RISA-932, RISA-953).
2. As the user on a second machine, I want the suite to read the fixture project's config whatever `RISA_CONFIG` my shell holds, so that 217 false failures don't hide real ones (RISA-975).
3. As the user on an old git, I want install and the test suite to refuse it with one line, so that no fixture ever touches my checkout (RISA-976).
4. As a project that installs Risa, I want to import `ci-runs.mjs` and the verdict fixtures by package name, so that my verdict test needs no file URL beside my own copy (RISA-970).
5. As a project, I want to import `BUDGETS` without the budget check running, so that I can check my role halves add up (RISA-971).
6. As a slice agent, I want `risa doc` and `risa project-check` in my worktree to read my worktree's config and files, so that I check my own change (RISA-972; built in `after-split-2`).
7. As the user of a stackless repo, I want `risa status` to say there is no test database, so that a working repo doesn't read as broken (RISA-977).
8. As a project's agent, I want the generic docs to name my project's command, so that every command I read runs (RISA-974).
9. As the user setting up a new machine, I want one ask naming `risa inbox` when the inbox can't open, so that I learn it without a dry run (RISA-978).

## Implementation decisions

- **The test environment** (the core's test setup): before any test, one pure function turns the inherited environment into the tests' own: the fixture config (or `RISA_TEST_CONFIG`), no machine config, no machine tag, and none of a session's state variables. It is the only place that knows the list. A git older than 2.28 stops the run in a Vitest global setup (once, before any file) with one line naming the version.
- **Fixtures' git init:** every fixture's init fails loudly (a thrown error), as `execFileSync` already does for most of them.
- **The git floor** (machine config's `check`): the same 2.28 floor, one line on failure, exit 2 like a config that doesn't load. One constant shared by both.
- **Package exports:** additive entries in `package.json`'s `exports`, proved by a test importing each through the package's own name. `docs-budget.mjs` exports `BUDGETS` and a pure `overBudget(dir)` returning the lines; the script part runs only when it is the main module.
- **Which config a worktree reads** (RISA-972, in `after-split-2`): the worktree's own `risa.json` when it has one, else the main checkout's; hooks still from the main checkout. Its planner must also tell a config risa inherited (every session gets the main checkout's `RISA_CONFIG` from the shell that opened it, through `find_repo`) from one a user pinned, in `lib.sh`, `bin/risa` and the session env.
- **Status's test-database line:** with no testDb hook (`has_hook`), one line saying none; with one, the hook's output or the failure line as today.
- **Generic docs:** `{{prd}}` in place of every literal `prd <command>` in `loops/docs/`; the budgets grow by what that adds; a doc test fails on a literal one.
- **The inbox report:** when the keep-alive holds the inbox for an untrusted or missing folder, the dispatcher files one report (the drain's `report` path: `ask.mjs --report`, topic `dispatch`) naming `{{prd}} inbox`, and records that it did in its state; trusted again clears the record, so a later spell reports again. A dry run says it would.

## Testing decisions

- The test environment: a unit test of the pure function (a session's environment in, the fixture's out; `RISA_TEST_CONFIG` kept). The proof is the slice's own check: run inside its orchestrator's session, which has the very variables that broke it.
- The git floor: unit tests with a stubbed version (2.24 refused, 2.28 accepted) for both the setup's check and `machine.mjs check`.
- Exports: one test importing each new export by package name, asserting no output and no exit on import.
- Status: a `stack.test.mjs` case on the existing no-stack-hooks config (prior art: the RISA-973 test).
- Docs: `doc.test.mjs` case over every generic doc; the budget check itself.
- Inbox report: `dispatch.test.mjs` cases beside the existing untrusted-inbox ones (one report across two ticks; again after trusted then untrusted).
