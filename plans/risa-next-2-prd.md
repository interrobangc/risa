## Problem

The user keeps ideas in an inbox, one file per project, on each project's public trunk: the lines are public, and every added line is a commit on the trunk. Each project also runs its own inbox session, so a user with two projects has two inbox sessions and must pick the right one. And the user runs Risa on more than one machine (Caretook's backlog runs on another one): nothing stops two machines from both running one project's dispatcher and backlog, whose locks are local, and the inbox on a trunk can only be written from a machine with that project's checkout.

## Solution

Each project can keep its inbox in one small private git repo the user owns, a file per project, which the tool writes through its own clone so two writers never lose a line. One inbox session per machine takes every idea, works out which project it belongs to (asking when it can't tell), and adds it there, for a project on any machine. The backlog session ingests from the repo and removes a line only once its item is safely on the trunk. The same repo records each project's home machine, so a second machine's dispatcher leaves a project alone until the user moves it. The user moves a project with one command when they choose; until then nothing changes.

## User stories

1. As the user, I want my inbox lines in a private repo, not on a public trunk, so that ideas aren't public (RISA-841).
2. As the user, I want adding an idea to make no commit on any project's trunk, so that the trunk's history is the work's (RISA-841).
3. As the user, I want one inbox session for all my projects that puts each idea in the right one and asks when unclear, so that I don't pick a session per project (RISA-841).
4. As the user, I want to add an idea for a project whose checkout is on another machine, so that the inbox works from wherever I am (RISA-841, RISA-1007).
5. As a backlog session, I want ingest to remove a line only after its item is on origin's trunk, and a rerun after a crash to file nothing twice, so that no idea is lost or doubled (RISA-841).
6. As the user, I want two racing writers never to lose a line, so that adding from two places at once is safe (RISA-841).
7. As the user, I want to move a project's inbox with one command, when I choose, so that nothing moves without me (RISA-841).
8. As the user, I want a second machine's dispatcher to leave a project alone while another machine is its home, and one command to move the home, so that two machines never run one backlog (RISA-1007).
9. As the user, I want the planning-store question weighed and answered on record, so that I can veto it (RISA-983, in RISA-841).

## Implementation decisions

### The inbox store

- A new deep module owns the inbox repo and is the only code that knows its clone: `storeFor(repo)` gives a store for a git URL, its clone under the machine's `.risa` folder (an env override for tests), made on first use. `read(file)` fetches (best effort; its last copy when offline) and returns the file's text or null. `write(file, edit, message)` fetches, applies `edit(text)` to the tip's copy, commits only that file, pushes without force, and on a refusal fetches and rebuilds, five tries; it returns the commit, or null when the edit changed nothing. It never touches a project's checkout.
- The line format is the trunk inbox's (`format.mjs`'s headings and bullets), so the parsers, the look-alike search and the edit helpers (`inbox-edit.mjs`) apply unchanged to a store file.
- The config gains the optional `inbox` group (`repo`, `file`); `file` defaults to `<name>.md`. A store file is a project: `--project <p>` names the file `<p>.md` in the store, whatever machine holds the project, so a custom `file` is reached by its own stem.
- `read(file, { fetch })`: `fetch: false` reads the clone's last fetched copy with no network (the dispatcher's cached read of the homes file).

### The inbox commands

- `backlog inbox add|edit|move|remove` and `backlog inbox` (list) go to the store when the config has `inbox`, else to today's trunk writer. Same arguments, same exit codes (3 for look-alikes), same one-line output naming where it wrote (`on <repo> <file> as <sha>`); no pickup after a store write.
- A store CLI runs the same commands with `--project <name>` from any folder, inside a repo or not (it needs no project config): the store module run directly with node, by its absolute path in the tool's install. The inbox session's prompt renders that command line. It finds the store from the machine config's repos (their `inbox.repo`, all equal) or the store's existing clone.

### Ingest from the store

- With `inbox` configured, ingest reads the store's file, files each new line as today (status inbox, its details in a note) and adds the line's key to that note; a line whose key is already in the backlog is not filed again. After the backlog commit it pushes trunk's backlog-only commits (the trunk writer's rule) and then removes from the store every line whose key is in origin's trunk's backlog, in one store write. A push it can't make leaves the lines for the next ingest.
- The doctor reports a store line whose key is filed but still there (fixable: the next ingest removes it).

### Moving a project

- `backlog inbox to-repo <git url>`: refuses unless `gh` says the repo is private; refuses with an `inbox` key already set; writes the unfiled trunk lines into the project's store file (merged with any there); then one trunk commit sets the `inbox` group in `risa.json` and removes the trunk inbox file. Filed (tagged) lines are dropped: their items hold them. `paths.inbox` stays, unread while `inbox` is set.

### One inbox session

- `risa inbox` with a store opens one session per machine: its prompt lists the projects (the store's files and the machine config's repos with `inbox`), routes a line to the project the user names or the one its words point to, asks in one line when unclear, and runs the store CLI (that rendered command line) with `--project`. Without a store the prompt is today's.
- For repos with an `inbox` key only: the keep-alive opens the inbox session only from the dispatcher of the machine config's first `work: true` repo with `inbox`, which also claims the `inbox` home on its first tick (as it claims its project's), and only while this machine holds that home; every other such dispatcher skips it with one log line. A repo without the key keeps its own trunk inbox session as today.

### Home machines

- A new module owns `homes.json` in the store: `homeOf(name)`, `claim(name, machine)` (writes only when unclaimed or already this machine's), `take(name, machine)` (overwrites, the user's command). The machine's name is the short host name; an env override for tests.
- The dispatcher, for a project with `inbox`, claims its home on its first tick, then fetches the store and reads the homes file at most every five minutes (every tick reads the last fetched copy), so a `take` elsewhere stops this machine within about five minutes; another machine's home makes the tick start, plan, reopen and keep alive nothing for that project, logged each tick, with one report naming both machines and `risa home take <project>`. A store it can't reach keeps the last answer (none on a first tick: it claims nothing and starts nothing until it can).
- `risa home` prints the claims; `risa home take <project|inbox>` moves one to this machine.

## Testing decisions

- **The store, unit:** bare repos in the OS temp dir as the "private repo", two clones racing a write (both lines kept, the loser rebuilt), offline read, five refusals give up with nothing written (prior art: `backlog/origin.test.mjs`).
- **The commands and ingest:** a sample project (`loops/sample-project/repo.mjs`) with an `inbox` key at a temp bare repo; ingest's crash between the backlog commit and the store write is a test (rerun files nothing twice and removes the line once origin has it); no-store projects pass every existing test unchanged.
- **The move:** a stub `gh` answering private or public; the trunk commit's two changes.
- **Prompts:** the golden render for the inbox session without a store stays as it is; a prompt test for the store form's project list and routing rule.
- **Homes:** temp store, two machine names by env; the dispatcher's dry-run tick shows the skip for another machine's project.

## Out of scope

- Creating the private repo, and moving Risa's or Caretook's inbox (the user's step, with the move command).
- Moving the backlog, registry or plans off git (weighed: _Decisions_).
- Cross-project work and reading other projects' backlogs (`risa-next-3`); machine-wide caps.
- Rewriting the public repo's history to drop old inbox lines.
