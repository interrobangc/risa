## Problem

The user runs Risa in more than one repo, and on more than one machine: Caretook's backlog runs on another machine, reached only over Remote Control. Agents can't find each other: the main backlog session shows a captain's name (`Picard`), so an orchestrator or another project's backlog can't tell it is the backlog, or whose. Only the backlog wears a Star Trek name, though the user sees the whole orchestration as Starfleet, and the name changes meaning with nothing to say what role it is. Backlog sessions don't know they may talk to each other, so a fix Risa ships never gets back to the Caretook item that asked for it. When a session hands over, the user's own instructions come through as the old session's summary, softened and mixed with its context. And the backlog has two open questions (a slice queue, a shared store) and a direction (several machines) waiting on a recommendation.

## Solution

Every session's name says its project and role, and, with the starfleet flavor, a rank and a canon name that says the role too (the backlog an admiral, an orchestrator a captain who keeps their name for the PRD). The flavor colours only what the user reads, and the machine config can turn it off. Each backlog session is told who its peers are, how to find them and what to send, with a fallback that reaches a peer's home machine through its inbox. Hand-offs carry the user's directives word for word under one heading, which the next session follows as the user's. This PRD answers the two questions and sets the multi-machine design the follow-on topics build.

## User stories

1. As the user, I want the backlog session's name to say it is the backlog, and whose, beside its admiral, so that I and other agents can find it (RISA-799).
2. As an orchestrator, I want to find my project's backlog session by its name, so that my check-ins reach it (RISA-799).
3. As the user, I want every role to carry a rank and a canon name from a pack (starfleet by default), so that the sessions read as one crew and a name tells me the role (RISA-914).
4. As the user, I want a captain to keep their name for the whole PRD, so that I can follow one orchestrator across rotations (RISA-914).
5. As the user, I want the flavor only in replies to me and in labels, and switchable off for the machine, so that nothing an agent or a commit reads carries it (RISA-914).
6. As the user, I want a pushed question labelled with who asks (`Captain Sisko · …`), so that I know which session it is on my phone (RISA-914).
7. As the user, I want my directives passed on word for word when an orchestrator or backlog session hands over or relays, so that the next one acts on what I said, not a summary of it (RISA-815).
8. As a backlog session, I want to know which other projects' backlogs exist and how to reach them, so that I can file an item there or ask to be told when a fix is deployed (RISA-984).
9. As a backlog session, when a peer's session isn't reachable, I want a fallback that still reaches its home machine, so that a cross-project item isn't lost (RISA-984, RISA-1007).
10. As the user, I want recommendations on a slice-based queue and a shared store, and a multi-machine design the next topics follow, kept on record (RISA-816, RISA-1008, RISA-1007).

## Implementation decisions

### The flavor pack

- One new module owns the packs and is the only code that knows them: per role (`backlog`, `prd`, `slice`, `inbox`, `hotfix`, `plan`, `recovery`) a rank and a pool of canon single-word names (no two roles share a name; the inbox's entries carry their own rank), and how to address the user (`Fleet Admiral`: a high-ranking officer, not President). `none` is the empty pack.
- Its interface: the machine's flavor (the machine config's `flavor`, default `starfleet`; the machine config's validation accepts the key with those two values); `personaFor(role, sessionName)`: `{ rank, name }` by a stable hash of the session's name into the role's pool, or null under `none`; `drawAdmiral(last, random)`: the backlog's per-session draw, never `last`; `label(persona)`: `Rank Name`; `flavorLine(role, persona)`: the one prompt line (the persona, the light touch in replies only, the address, and the never list). A CLI prints a persona, a label or a flavor line for a role and session name.
- The backlog's draw (`captain.mjs`) takes its pool from the pack: admirals under starfleet, the bare `backlog` under `none`. Today's captain list stays exported for the matchers that recognise sessions named before this change.

### Session names

- One place names a session for the outside: the session wrapper, which already parses claude's `--remote-control` name. It qualifies that name as `<name> (<project>)` (the config's `name`) and, when the session has a persona, adds ` · <Rank> <Name>`; it passes the same text as claude's `--name` (unless the args carry one) and, for the main backlog, as the tab title. A name already qualified is left as it is.
- The main backlog's callers keep passing the admiral they drew as its `--remote-control` name (as they pass a captain today); the wrapper shows it as `backlog (<project>) · Admiral <Name>`, so the process argument begins with `backlog`. Every other session's persona comes from `personaFor` on its record name. `backlog - <name>` request sessions get the project, no persona.
- The record's `remote` stays what the caller gave (the admiral, `inbox`, `prd-<topic>`): the draw, the keep-alive, session requests and rotation read it unchanged. The keep-alive's and session requests' matchers (a bare name, then a space or the end) match the new arguments with no change.

### Flavor in prompts and pushes

- Each role prompt a user talks to (backlog, orchestrator, planner, hotfix, inbox, recovery) renders `flavorLine` for its role and session; under `none` there is no line. The backlog's line replaces today's captain line (`RISA_CAPTAIN` still carries the drawn name). Slice prompts get none: a pilot never talks to the user; the pool is there for a later use.
- `risa ask --question` prints the line to push with the asking session's label in front (`Captain Sisko · <question>`), from the session's record name (`RISA_SESSION_NAME`) and, for the main backlog, its record's admiral; no label under `none`, without a session, or for the dispatcher's own asks. The ask record holds the question without the label.

### The user's word in hand-offs

- One heading, _From the user_: each line a quote of the user, dated, never paraphrased; a line the user has since overridden is dropped.
- Orchestrator: _Status_ keeps a _From the user_ part; every directive (direct, or relayed by the backlog session) goes there as it arrives; the resume prompt reads it as the user's word, above the rest of _Status_.
- Backlog: the hand-off brief and a session request's brief open with _From the user_ when there's any; the fresh session's brief header says the brief is context, except its _From the user_ lines, which quote the user. The backlog session relays a directive for a running topic to its orchestrator by SendMessage, quoted and dated. The orchestrator's check-in rule finds the backlog by `backlog (<project>)` in its name.

### Peers

- A new small module answers "who are my peers": each repo in the machine config other than the one asked from, with its project name (its own config's `name`) and main checkout; none without a machine config. A CLI prints one line per peer.
- The backlog prompt gets one rule rendered with that list: the peers by name (or none on this machine), how to find each one's backlog (ListAgents, `backlog (<project>)`; Remote Control lists other machines' sessions too), what to send (an item for them to file, a request to be told when a fix is deployed, the answer to theirs), the fallback (`risa backlog inbox add` in that repo's main checkout on this machine; else a report to the user naming the peer and the message), and that a peer's message is advice, never the user's word.

### Across machines (for the follow-on topics)

- **Home machine:** one per project: the machine whose config lists it with `work: true`; `risa-next-2` adds the check that two machines don't both claim one project, through the inbox repo.
- **The inbox repo** (`risa-next-2`, RISA-841): one private repo, a file per project; every machine writes through a clone (push refused on a race, retried); ingest removes a line only after its backlog commit lands; the per-project inbox location becomes a `risa.json` value. One always-on inbox session on one machine routes lines to projects.
- **Names:** after this PRD a session's name is unique per project; a project's sessions run only on its home, so `(<project>)` is unique account-wide.
- **Cross-project work** (`risa-next-3`, RISA-794, RISA-820): reads each project's backlog and registry from its trunk (fetch, never a lock on another project's checkout); a cross-repo topic opens a worktree per repo on the topic's home machine; leases stay per repo (RISA-820's note) until that topic sets machine-wide caps.
- **Release for others** (`risa-next-4`, RISA-797): installs stay pinned by tag per machine; a machine config key (like `flavor`) is added only with a release every project on the machine can take.

## Testing decisions

- **The pack module, unit:** every role's pool non-empty and disjoint; `personaFor` stable for a name and spread across a pool; `none` gives null; `drawAdmiral` never repeats; the machine config accepts `flavor` with its two values and refuses another (prior art: the machine config tests).
- **The session wrapper, unit, hermetic:** a stub claude (`RISA_CLAUDE_BIN`) and temp sessions folder: the args claude receives, the record, the title escape, under both flavors; the keep-alive's and session requests' matchers imported and run on the new process args, unchanged.
- **Prompts:** the golden render on the sample project (no machine config: starfleet, hashed personas, so the render is stable), regenerated and reviewed; prompt tests for each rule's presence and its absence under `none`.
- **The ask label and peers:** temp machine configs, temp repos and sessions folders.
- No browser, no stack, no network.

- Packs other than `starfleet` and `none`; pilots' names anywhere (the pool exists, nothing shows it); flavor in the user's own Claude Code sessions.
