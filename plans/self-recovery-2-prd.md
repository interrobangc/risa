# PRD: Finish what landed, and count what it cost (self-recovery-2)

Backlog items RISA-811 (cleanup finishes a landed PRD left half-done), RISA-789 (a dead landing journal holds a resume with only a waits line) and RISA-560 (the cost record). RISA-438 (headless orchestrator sessions), RISA-912 (slices as their own headless sessions) and RISA-913 (long work as jobs the machinery owns) move to the follow-on topic `self-recovery-3`, after this one.

This replaces the PRD moved from Caretook with B-543. Since it was written, RISA-811's three named causes landed there (B-431: `rm` marks a topic with a docs-only tail done and `landed.mjs` decides it; B-812: `rm` ends its own caller; B-810: `end` ends only the session's claude) and the dispatcher's pick never starts a landed topic (`dispatch-pick.mjs` rule 8). What is left of RISA-811 is the cleanup itself: nobody runs `rm` for a landed topic whose orchestrator stopped short.

## Problem

A topic can land and still hold a lane. When its orchestrator stops short of `rm` (a usage limit, a crash, a rotation at the wrong moment), its worktree, slot and sessions stay, its row stays `planned` or `running`, and nobody cleans up until the user runs `rm` by hand. The dispatcher no longer restarts it, but it doesn't finish it either. Several sessions of one topic can be live at once and nothing says so.

A session whose resume after a usage limit is held by a dead landing journal waits forever, with one log line per tick that no one reads. And nothing says what a PRD or a slice cost in tokens.

## Solution

A topic that landed gets finished by the machinery: once its sessions are idle, the dispatcher ends them, removes the worktree through `rm` (which lands or drops a docs tail and marks it done) and files one report. A tail with code is reported and kept. Tidy lists duplicate live sessions of any topic. A dead landing journal that holds a resume reaches the user as one report naming the command. `risa cost` shows tokens by model for each PRD and slice, kept after the transcripts are gone.

## User stories

1. As the user, I want a landed topic whose orchestrator stopped short cleaned up by itself (sessions ended, worktree and slot removed, row done), with one report, so that it never holds a lane. (RISA-811)
2. As the user, I want a landed topic whose tail has code reported and never removed, so that unmerged work is never lost. (RISA-811)
3. As the user, I want the cleanup to wait while any of the topic's sessions is still working or a landing is in flight, so that it never cuts off a session finishing itself. (RISA-811)
4. As the user, I want to run the same cleanup by hand, or see what it would do, for one topic. (RISA-811)
5. As the user, I want tidy to name a topic with more than one live session, and a landed topic with leftovers when the dispatcher isn't running, so that I see what the cleanup would act on. (RISA-811)
6. As the user, I want one report when a dead landing journal holds a session's resume, naming the `land --resume` to run, so that a limit doesn't silently cost a whole session. (RISA-789)
7. As the user, I want `risa cost` to show tokens by model for each PRD and each slice, from session and subagent transcripts, so that I can see what work costs. (RISA-560)
8. As the user, I want the cost record to survive a topic's removal, transcript cleanup and `--continue`, with nothing counted twice, so that the numbers stay right. (RISA-560)

## Implementation decisions

- **The finish decision** (a new pure module, `finish`): facts in (the topic, whether it is landed and at which sha, its tail kind, its worktree and slot, whether the worktree is dirty, its slice worktrees left, its registry row, its recorded live sessions with their heartbeat (running calls, last event), any other live claude in its worktree, whether a landing journal exists for its branch, the time, the idle minutes, the reports already filed); out: `running` (not landed), `clean` (nothing left), `wait` (a busy session or a journal, with why), `act` (the recorded sessions to end, then `rm`), or `report` (a code tail, a dirty worktree, slice worktrees left, an unrecorded claude, a recorded session with no heartbeat, or no worktree with a slot or an open row left: once per topic and reason and tip, nothing ended). A `standing` topic is always `running`. Every `report` reason is checked before `act` is possible.
- **Landed with code** (in `finish`): the topics whose last landing is in the trunk and with code past it, from `landed.mjs`'s `lastLanding` and `tailOf`; `landedTopics` is unchanged. The dispatcher's step and tidy read both sets.
- **Live sessions of a worktree** (the session records module): every live claude whose working directory is in a given worktree, recorded or not, from the process table and `cwdOf`; the finish facts and tidy share it.
- **`risa finish <topic> [--dry-run] [--json]`**: gathers the facts, applies the decision: ends each session through `end`'s own check (never a pid that isn't the session's), runs `rm <topic>` from the main checkout (no `--force`), files one report (session `finish`) naming what it did, or what it kept and why. `--dry-run` prints the decision and acts on nothing.
- **The dispatcher's finish step**: after the pick, for the landed topics (either set) that have a worktree, a slot or a row not done, it applies the decision to the first one each tick whose decision is `act` or a report not yet filed (topics that wait, or whose report is filed, are passed over), never while paused or draining. The reports it filed are kept in the dispatcher's state (`finish.reported`, by topic and tip) so a kept code tail is reported once.
- **Tidy**: its ask list names a landed topic (never a standing one) with leftovers (when no dispatcher runs) and any topic with more than one live claude in its worktrees.
- **The journal report** (the resume step): the dispatcher hands the resume decision the journals with their pid's liveness. A claim waiting on a journal whose pid is dead files one report naming the session, the branch and `risa land --resume <branch>`, recorded in the claim (`journalReported`, the journal's branch and start) so it's filed once per journal. A live journal stays a waits line.
- **The cost record** (a new pure module, `cost`, and `risa cost [<topic>] [--json]`): reads the transcripts in Claude Code's project folders for the topic's worktrees (`<topic>`, `plan-<topic>`, `<topic>-<n>`), the subagent transcripts beside each session, and the ledger. Each assistant message counts once, by message id, across every file (the last line of a streamed message wins). A subagent's tokens go to the slice its description names, else the slice worktree its first prompt names, else the topic's orchestration line; a `plan-` worktree's go to planning. Output per topic: planning, orchestration, each slice, and the total, each as tokens by model (input, output, cache read, cache write). Malformed lines are counted and skipped. The projects folder is `CLAUDE_CONFIG_DIR`'s, else `~/.claude`'s, overridable for tests (`RISA_CLAUDE_PROJECTS`).
- **The ledger**: `rm` of a `prd/` or `plan/` worktree runs `cost ledger <topic>` before removing it, which merges what's on disk into `.loops/.cost/<topic>.json` (rows by message id: model, the four counts, the line it belongs to). A failure prints one line and never fails `rm`.

## Testing decisions

Unit tests for each pure decision with fictional fixtures: the finish decision (not landed, clean, each tail kind, a busy session, an idle one, an unrecorded claude, a dirty worktree, slice worktrees left, a journal, a code tail already reported, a standing topic, no worktree with an open row, no heartbeat record), the pick over two topics where the first is stuck, landed with code on a temp repo, live sessions of a worktree from a stub process table, the journal report's once-only rule (dead, live, the same journal twice, a new journal), the cost parser (dedupe across files and `--continue`, streamed repeats, attribution by description, by prompt and neither, planning, malformed lines, the ledger merge). Script-level tests with stubs and temp directories, after `tidy-cli.test.mjs` and `resume.test.mjs`: `risa finish` on a temp repo whose topic landed with a docs tail ends the stub session, removes the worktree and files the report; with a code tail, a dirty worktree or a slice worktree left it ends nothing, keeps everything and reports once; the dispatcher's step reports a code tail once over two ticks; `--dry-run` acts on nothing; `rm` writes the ledger and still succeeds when the ledger write fails. Tests for this topic go in their own files, never `dispatch.test.mjs` or `stack.test.mjs` (`after-split`'s files). No test touches the real session records, asks, transcripts or `~/.claude`.

## Out of scope

- Headless sessions and machinery-owned jobs (RISA-438, RISA-912, RISA-913): `self-recovery-3`.
- Dollar costs, price weighting (RISA-883), budgets or limits on the cost record.
- Cleaning up a topic that never landed.
- Ending a duplicate session of any topic, or any claude the session records don't name.
