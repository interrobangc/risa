## Problem

A topic whose plan turns out wrong has no way back to its planner short of hand edits to the plan and the registry, and nothing stops its orchestrator from running the next wave from the old plan meanwhile. An orchestrator that lands a wave and then stops without its rotate step (seen twice on 2026-11-28) holds its lane until someone notices, and a topic whose last wave landed with its row still `planned` reads as waiting and fills the lookahead. And the headless sessions planned next (RISA-438, RISA-912, RISA-913) rest on Claude Code features nobody here has tried with Risa's Remote Control, status line and hooks.

## Solution

The user flags a topic `replan`. Before it runs, the dispatcher plans it again. While it runs, it starts no new slice, lands what is in flight, and closes at the next hand-over; the dispatcher plans it again from the trunk, and the new plan picks up where the landed work stopped. Every rotation is in the run log; the dispatcher catches a standing (or `replan`) topic whose orchestrator landed and went idle without rotating, reports it, then runs the rotation itself. A topic whose work is all landed but whose row says `planned` no longer holds the lookahead. A spike tells the next planner what Claude Code's background sessions can do.

## User stories

1. As the user, I want to flag a topic `replan`, so that the dispatcher sends it back to its planner to replan the whole PRD (RISA-998).
2. As the user, I want `prd list` to show a flagged topic as `replan`, so that I can see it is waiting for its planner (RISA-998).
3. As the user, I want a running topic's replan to wait for its wave in flight to land, so that no slice is cut off and no work is thrown away (RISA-998).
4. As the orchestrator of a topic flagged `replan`, I want `risa slice` to refuse a new slice, so that I land what is in flight and stop at the boundary (RISA-998).
5. As the replanning planner, I want to read what already landed, so that I rewrite only the slices still to run (RISA-998).
6. As the user, I want each rotation in the run log, so that a landing not followed by a rotation shows (RISA-1040).
7. As the user, I want a standing topic whose orchestrator landed and sat idle without rotating to be reported and then rotated by the dispatcher, so that its lane is freed (RISA-1040).
8. As the user, I want a topic whose work all landed but whose row stayed `planned` to stop filling the lookahead, and to be told how to mark it done (RISA-1040).
9. As the `self-recovery-4` planner, I want a written account of what Claude Code's background sessions do with Remote Control, the status line and hooks, so that I plan headless sessions on facts.

## Implementation decisions

- **The replan flag.** The registry's flags gain `replan` and its states gain `replan`. A topic's state is `done`, then `running` (a worktree), then `hold`, then `replan` for a flagged row, then as now. Setting and clearing go through the existing `flags+=` and `flags-=` edits. Nothing else in the registry changes meaning.
- **The replan dispatch.** The pick's planning rule takes `replan` rows beside `to-write` ones, in row order, under the same `after`, planner-cap and lookahead rules, without the waiting-items test; its reason says the row is flagged. A plan worktree whose row is still `replan` counts as a planner at work. A `replan` row with a prd worktree is `running` and left to its orchestrator (a dead session is reopened as now: the reopened one closes at its next hand-over).
- **The replanner's prompt.** The planning prompt gains one bullet, present in every planning prompt: when the PRD and plan are already on the trunk (a replan), read them, the items, and `prd/<topic>`'s _Status_ when that branch exists (it is newer than the trunk's); keep each landed slice and its _Status_ row as they are; rewrite, add or drop only slices not landed; record the change under the Decisions table; run the skeptic as usual; clear the flag before landing.
- **Rotate.** Rotate appends one `rotate` event per run once it knows the topic: `opened` (handed to rotate-into), `closed` (the standing close), `replan` (below) or `refused` (a guard stopped it, with its line). After a landing, before the standing-close test, a row flagged `replan` closes: `rm` from the main checkout, then the session ends, one line saying the dispatcher plans it again; a failed `rm` leaves the session running, as the standing close does. A pure `replanClose(rows, topic)` decides it; the same rows answer `new.sh`'s refusal of a slice for a flagged topic. The standing close's own pick treats a `replan` row as it treats a `to-write` one.
- **The land-idle backstop.** A new pure decider takes, per topic, its row, its managed live session record (name, `started`), that session's heartbeats, its last landed `land-end` and last `rotate` event, rotate's standing-close reason, the dispatcher's paused and drain state, the clock and its own state; it returns per topic `nudge`, `rotate`, `report-refused`, `report-spent` or nothing, and the next state. Idle is finish's idle reading (no call running in any heartbeat record, the last event older than the window), shared, not copied. The tick runs it after the finish step: a nudge or report is one ask report under session `land-idle`; `rotate` runs `rotate.sh <topic>` from the main checkout and reports its first line. Its state is `landIdle` in the dispatcher's state file, one entry per topic keyed by the landing's time, dropped when a later rotate, landing or session end makes it moot.
- **The spike.** No code. It tries each background-session command and each of Risa's needs (Remote Control by name, the status line's `rate_limits`, the heartbeat hooks, the session record's pid and liveness, the per-account Claude config folder, resume, stop, a machine sleep) and writes what it saw, with the Claude Code version, as a table and a recommendation per item (RISA-438, RISA-912, RISA-913).

## Testing decisions

- Each code slice has one unit test file (its `Check:`). Pure deciders (`stateOf`, the pick, `replanClose`, the backstop) are tested on facts, as `dispatch-pick.test.mjs` and `dispatch-stuck.test.mjs` do. Rotate's events, its replan close and `new.sh`'s refusal are tested in `rotate.test.mjs` with its existing standing-topic fixtures (a registry written by hand, a stub claude, `RISA_RUN_LOG`). The prompt bullet is checked by the prompt golden file.
- The backstop's tick wiring is covered by its decider's test and the dispatcher's header; no case is added to `dispatch.test.mjs`.
- No test starts a real Claude Code session. The spike is checked by reading its doc.

## Out of scope

- Headless sessions of any kind (RISA-438), slices as their own sessions (RISA-912) and jobs the machinery owns (RISA-913): `self-recovery-4`, planned from the spike.
- A non-standing topic that lands a middle wave and then stops: the stuck check's quiet question (30 minutes) already asks about it.
- Fixing why `rm` left self-recovery-2's trunk _Status_ showing a slice at work: the backstop reports the spent row; the cause is a fix topic's if it recurs.
- A queue tender (RISA-1036, `asks-relay`): the backstop is one check it may later own.
