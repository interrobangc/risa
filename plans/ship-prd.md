# PRD: Ship, one command to ship a pinned version

Backlog item RISA-1053: a generic `risa ship <version>` with one shared scaffold (pre-checks, ship steps, a smoke test, a notification), each a hook a project overrides. Risa's own hooks are built here. Caretook's staging and production promotion becomes its own override later (`staging-ship`, held, replanned around this scaffold; its hooks live in Caretook's repo).

## Problem

Risa ships pinned versions (`v0.1.0` to `v0.2.0`), each by hand: bump `package.json`, commit, tag, push, install it somewhere, try it, tell the projects that pin it. Nothing checks that CI passed first, a missed step goes unnoticed, and a project learns of a release only if someone tells it. Caretook ships too (staging, then production), with its own steps and the same need for checks before, a smoke test after and a word at the end. Each project growing its own command would repeat the scaffold.

## Solution

`risa ship <version>` runs the same four phases in every project: pre-checks, the ship steps, a smoke test and a notification. The tool owns the order, the record, resuming and the report; each phase is a hook the project's `risa.json` names, so the project says how it ships. Risa's hooks bump, tag and push, install the tag and try it, and tell the projects on this machine that pin an older version. The user says "ship 0.2.1" (or runs the command) and reads one report.

## User stories

1. As the user, I want one command, `risa ship <version>`, to ship a version, so that I don't run the steps by hand (RISA-1053).
2. As the user, I want every project to ship through the same phases (checks, steps, smoke test, notification), so that each ship is checked and announced the same way (RISA-1053).
3. As a project, I want to say how I ship through hooks in my config, so that the scaffold runs my steps (Risa's tag, Caretook's promotion) (RISA-1053).
4. As the user, I want a failed ship to resume where it stopped, so that a smoke failure doesn't push a second tag (RISA-1053).
5. As the user, I want to try a version's checks without shipping it, so that I see what would stop it (RISA-1053).
6. As the user, I want one report when a ship ends, saying what shipped, what was tried and who was told, or where it stopped (RISA-1053).
7. As the user, I want Risa's ship to refuse a version whose CI didn't pass, or that is already tagged or not above the last, so that a broken or duplicate release can't go out (RISA-1053).
8. As the user, I want Risa's ship to bump, commit, tag and push in one step that leaves the main checkout alone (RISA-1053).
9. As the user, I want Risa's ship to install the tag and try it, so that a release that won't start is caught before a project takes it (RISA-1053).
10. As a project pinned to Risa on this machine, I want to hear that a newer version is out, so that I can take it (RISA-1053).

## Implementation decisions

### The ship module

A new command, `risa ship <version> [--dry-run] [--from <phase>]`, over a small module that owns the phases. Its pure core decides the next phase from a record and the options; a runner calls the hooks through the existing hook runner and writes the record after each phase.

- **Phases:** `check`, `ship`, `smoke`, `notify`, in that order, each one hook (`shipCheck`, `ship`, `shipSmoke`, `shipNotify`), each called with the version as its argument and `RISA_SHIP_VERSION` set. The config's shape gains the four keys as optional commands.
- **Generic pre-checks,** before any hook: the version has the config's version shape; the project sets `hooks.ship`; the version's record isn't finished; no other ship of the project is running.
- **The record:** `.loops/.ships/<version>.json` in the main checkout (`RISA_SHIPS_DIR` overrides it, as the asks and notices directories are), holding `{ version, startedAt, phases: [{ name, ok, at, facts, tail }], doneAt }`. A running ship holds the folder's one lock file (`.lock`, carrying its pid), so no two ships of a project run at once whatever their versions; a dead pid's lock is taken over. `--from <phase>` drops that phase's result and every later one before running, on a finished record too (to notify again, say); without it a finished record refuses.
- **Output:** each phase prints a line as it starts, the hook's output when it ends, and `skipped` for a missing optional hook. Exit 0 when shipped, 1 when a phase failed, 2 when refused (usage, pre-checks, finished, running).
- **The report:** one report in the project's asks (topic `ship`) when the ship finishes (each phase's result, the facts the hooks printed, the phases skipped) or when a phase fails (the phase, the last lines of its output, and `risa ship <version>` to resume). A `--dry-run` files none.

### Risa's hooks

`release/ship.mjs`, one file with four verbs (`check`, `ship`, `smoke`, `notify`), each the hook for its phase in this repo's `risa.json`. `release/` joins the config's tooling paths and the tests' `tooling:unit` project.

- **check:** fetches `origin`; refuses a tag `v<version>` already on `origin`, a version not above the highest `v*` tag, and a release base without a successful `ci.yml` run (the base is `origin/main`'s newest commit that changes more than the backlog's files, since most pushes are backlog commits whose CI may still be running; a run in progress refuses with a line saying to try again) (read through the existing CI reader in `ci/`, `listRuns` and `WORKFLOW_NAME`, not a new `gh` call). Prints `tip=<sha>`.
- **ship:** in a temporary worktree detached at `origin/main`: checks CI on that tip again, sets `package.json`'s version (no other byte changes), turns `CHANGELOG.md`'s `## Unreleased` into `## v<version>` under a new empty `## Unreleased`, commits `chore(release): v<version>`, pushes `HEAD` to `main` (no force), makes the annotated tag and pushes it, then removes the worktree. A tag already on `origin` whose commit's `package.json` has the version is done: it prints the facts and exits 0. Prints `tag=v<version>` and `commit=<sha>`.
- **smoke:** installs the tag at `$HOME/.risa/releases/v<version>` as the README does (reusing one already at the tag, refusing one at another commit), then runs from it: `loops/machine.mjs check`, `bin/risa --root` (it must print the install), `bin/risa doc planner`, and `bin/risa backlog list` from this repo's main checkout. Each must exit 0. Prints `install=<dir>` and `link=ln -sf <dir>/bin/risa ~/.local/bin/risa`.
- **notify:** for each repo in the machine config other than this one whose config sets `risaVersion` below the version, files a report in that repo's asks (topic `risa-release`) through the new install's `bin/risa`, run from that repo with `RISA_ASKS_DIR`, `RISA_SHIPS_DIR`, `RISA_SKEPTIC_DIR`, `RISA_NOTICES_DIR`, `RISA_CONFIG` and `RISA_CONFIG_FOUND` removed from its environment (the ship's own, which the hook inherits, would file the report in Risa's asks). Prints `notified=<name> (<their version>)` for each, and `elsewhere=cross-machine-messages (RISA-1055)`.

### The doc

A short generic doc, `ship` (`risa doc ship`): the phases, the hook contract, the record and resuming, the report, and the rule that only the user's word starts a ship. `AGENTS.md`'s release line points at the command, and `CHANGELOG.md` names the new doc's headings, as the headings check requires.

## Testing decisions

- **The ship module:** unit tests of the pure next-phase decision (fresh, resumed, `--from`, finished), and command tests with the fixture project's config pointing its hooks at stub scripts in a temp repo, `RISA_SHIPS_DIR` and `RISA_ASKS_DIR` at temp folders: phase order, a skipped optional hook, a failing phase and its resume, `--dry-run`, a finished version refused, a held lock refused and a dead one taken over, the report's text. Prior art: `loops/hooks.test.mjs`, `loops/notices.test.mjs`.
- **Risa's hooks:** command tests against a throwaway repo with a bare `origin` (`loops/sample-project/repo.mjs` `makeRepo`, `loops/land-fixture.mjs`), a fake `gh` on `PATH`, `HOME` and `RISA_MACHINE_CONFIG` at temp paths. The smoke test's install is the throwaway repo's own tag, so its `bin/risa` is this checkout's code at that commit; its `backlog list` reads a sample project, never this checkout's backlog. The notify test runs with the shipping repo's `RISA_ASKS_DIR` set and still finds the report in the other repo's asks.
- **No test pushes to the real `origin`, tags this repo, or writes the real `~/.risa`.** The first real ship is the user's word, after this lands.
- Tooling only: `pnpm check`. No browser checks.

## Out of scope

- Caretook's hooks (its staging and production promotion): they live in Caretook's repo, and `staging-ship` is replanned around this scaffold when it is lifted.
- Telling projects on other machines (`cross-machine-messages`, RISA-1055).
- Relinking `~/.local/bin/risa`, and a project taking the new version (bumping its `risaVersion`).
- Enforcing `risaVersion` (`risa-next-5`, RISA-1017).
- A changelog, release notes or a GitHub release.

## Notes

- The dispatcher runs from a release install and checks between ticks where `risa` points; a ship that doesn't relink leaves it alone.
- The first ship runs from the checkout (`~/git/risa/bin/risa ship …`): the installed `v0.2.0` has no `ship` command.
- `v0.2.0` (commit `4271285`, `chore(release): v0.2.0`) is the shape the ship step makes.
