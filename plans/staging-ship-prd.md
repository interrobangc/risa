## Problem

Getting `dev` onto staging takes a person through a dozen steps: push, cut a candidate, wait for CI, wait for Codex, read each finding against the code, file the real ones without duplicates, reply and resolve each thread, promote, watch the deploy, and work out what to try. Each step is a place to stop for hours or to get it wrong. Orchestrators repeat the Codex part by hand on every PRD pull request. When a ship finishes, nothing says what reached staging or what to test there.

## Solution

The user says "deploy staging" in a backlog session, or runs `pnpm prd ship --open`. A ship session pushes `dev`, cuts or resumes the candidate, waits for CI and Codex, verifies each finding and files it through one tool, merges when nothing blocks, watches the deploy, writes a to-test file and pushes the result to the phone. The user hears from it earlier only when something needs them: a blocker, a failed check, or no review. The same findings tool serves orchestrators on PRD pull requests.

## User stories

1. As the user, I want one word or command to take `dev` to a deployed staging, so that I don't run the steps by hand (B-404, B-584).
2. As the user, I want a ship to use the candidate gate, so that nothing reaches staging without its whole-suite run (B-404).
3. As the user, I want a ship to merge by itself when nothing blocks, so that I'm only interrupted when I'm needed (B-404).
4. As the user, I want a blocker to stop the merge and reach my phone, so that a broken release doesn't deploy while I'm away (B-404).
5. As the user, I want to decide whether a release ships without a Codex review, so that an outage at Codex doesn't quietly remove a check (B-404).
6. As the user, I want a stopped ship to resume where it was, so that an answer or a fix doesn't mean starting over (B-404).
7. As the user, I want the deploy's result on my phone, success or failure, so that I know when to look (B-584).
8. As the user, I want a to-test file for each ship, saying what reached staging, what to try and what wasn't checked (B-436).
9. As an orchestrator, I want Codex's findings filed by one command, verified and without duplicates, so that I stop doing it by hand (B-430).
10. As an orchestrator, I want each filed or declined finding replied to and resolved in the same step, so that no thread is left behind (B-430).
11. As anyone reading a verdict, I want a PR with more than 100 threads read in full, so that it can't read as clean by accident (B-241).

## Implementation decisions

- **Codex's verdict on a candidate.** The review command accepts an `rc/` branch and reads its PR into staging. A candidate's verdict never carries over from an older commit: it must be on the exact tip. The PR's threads and their comments are read in full across pages; if they can't be, the verdict is not clean. If Codex shows no sign of starting within five minutes of a new tip, the tool asks it once for that tip with `@codex review`. On a candidate, a usage-limit comment counts only when it is newer than the tip's commit; an older one leaves the tip waiting. `review --resolve` refuses a candidate's threads and points at `findings`.
- **The findings module** (`pnpm prd findings <topic|branch>`). A small interface over a PR's open findings: `list`, `file <thread> <type> <title>`, `note <thread> B-<n>`, `decline <thread> --skeptic <id> --why <text>`, `blocker <thread> --why <text>`, `fixed <thread> <commit>`. Filing runs the backlog's look-alike search and stops on a match unless given `--anyway`. `fixed` accepts a commit on the candidate's tip that isn't in the history the finding was raised on, or a dev commit whose cherry-pick (by its `cherry picked from` trailer) is on the tip. Each item carries a `[codex-finding <pr>/<thread>]` mark, so a retry after a crash finds the item instead of filing another. `file`, `note`, `decline` and `fixed` reply on the thread and resolve it; `blocker` replies with the `[ship-blocker]` mark and leaves it open. On a candidate, `file`, `note` and `decline` refuse a marked thread, a P0 or an unbadged finding unless given `--ask <id>`, an ask bound to `clear-finding`, this tip and this thread. The verdict on a candidate counts a resolved P0 or marked thread as open unless its last write-access reply is a valid `fixed` or bound-ask clearing.
- **Bound asks.** A question can be filed with a binding (an action, a tip, a thread), stored in its record. The check requires the exact binding, the first option answered (the yes), `--waits` and no default. `pnpm prd answer` records no identity, so "the user's answer" rests on sessions only recording what the user said: an honor-system limit.
- **The ship module** (`pnpm prd ship`). A sequence that works its state out from GitHub and git, with no state file: push `dev` through the same step `pr` and `land` use, cut the candidate, wait for its CI verdict, wait for Codex on its tip, then promote. A fresh ship runs its refusals before any push: it refuses when a candidate is open or the latest promotion's deploy run hasn't concluded, and points at `--resume`. `--resume` never cuts. Whether a ship was Markdown only is read from its merge's diff. When the latest promotion's to-test report is missing from this machine, `--resume` or the next fresh ship writes it first, so a lost file never wedges a ship. It exits with a distinct status for each stop: ready, findings to triage, blocker, CI failed, no review, staging moved, merged but unfinished, nothing to ship. It prints what to do next.
- **Promotion pinned to a tip.** `promote` gains an optional expected commit and refuses if the candidate has moved. Ship passes the commit both checks passed. Promotion's other rules are unchanged.
- **The deploy watch.** After the merge, ship finds the `deploy.yml` run for the merge commit and waits for it. A run that never appears, or fails, is a failed ship: staging keeps its previous deploy, and the tool says so.
- **The to-test report.** A pure builder takes what shipped (the items and commits between the old and new staging, the candidate's verdict, flakes, findings filed, declined or skipped) and returns the file's text. Ship writes it to `to-test/` in the main checkout, even when the deploy failed, and says so at the top.
- **The ship session.** `pnpm prd ship --open` opens a session in a stackless worktree detached at `origin/dev`, makes no candidate itself, and moves the worktree to the candidate's tip after the cut and after each `candidate fix`, so findings are read against the code being shipped. The backlog prompt learns the "deploy staging" trigger. The session's prompt holds the blocker rule, the question it files for each stop, and the one push at the end.

## Testing decisions

- Unit tests for the pure parts: the verdict on a candidate (exact tip, no carry, paged threads), the ship's next-step decision for every state, the finding mark, the report builder.
- Command tests with fake `gh` and throwaway repositories, the prior art being `promote.test.mjs`, `candidate.test.mjs` and `codex-review.test.mjs`, with fixtures of real PR states.
- **No test or slice makes a real candidate, CI run, PR comment or merge.** The first real ship is the user's word, after this lands.
- Tooling only: `pnpm test:tooling` and `pnpm exec eslint scripts`. No browser checks.

## Out of scope

- Shipping staging to production: `pnpm prd ci release` stays as it is.
- Why pushes don't reach the phone (B-586, `fixes-tooling`). The ship sends its push and never claims it arrived.
- The other review tool bugs (B-239, B-240, B-244) and promotion's flake filing (B-681) stay in `fixes-tooling`. Ship reads the verdict through the module and has its own wait, so it doesn't depend on them.
- What "live" means in the backlog (B-459).
- Fixing a blocker: the ship stops, and the fix goes through `dev` and `candidate fix`.
